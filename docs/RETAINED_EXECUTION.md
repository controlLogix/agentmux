# Retained approved task execution

`RetainedExecutionOwner` composes the selected approved plan, task container and
fixed task credential owners. The native host selects one execution ledger and
the separately enrolled service signer. Constructing these objects grants no
permission. Plugin requests cannot choose a command, environment, mount, network,
credential issuer, broker destination or Docker operation.

The first start saves the exact signed request, executor version, run and attempt,
approval deadline and container preparation effect before creating private task
credentials or a container. Later records use distinct enrolled service operations
and the execution ledger sequence. They do not replace the original request or
extend its permission. Equal start replay checks the original approved plan and
current task reservation again; changed content under the same original refuses.

For the native caller, each delivery carries a fresh signed proof lasting at most
five seconds. The first accepted proof also fixes a separate finite execution
ceiling from the operation, current authority, native session, human terminal
session, approved plan and task limits. That ceiling bounds the original
credential generation. Fresh delivery evidence must match the complete original
operation and payload, and cannot extend that ceiling or replace saved bytes.
Legacy records retain their original bounds; an expired credential is never
reissued to revive an old execution.

One live public admission creates private completion ownership for that call.
Internal steps may finish after its delivery proof expires while checking current
grants, identity, native and human sessions, task and plan at the real current
time. Public admission and retries always need a fresh live delivery proof; they
cannot accept the private completion object. If the original observer's proof
expires during completion, its result is withheld. A fresh authorized service
query can report the retained execution state.

Preparation returns a pending enrollment state. The native administrator can
retrieve the public enrollment proof under a fresh service read. The existing
organization administrator must apply that proof through the identity owner.
The task cannot approve itself. Dispatch then creates the exact approved isolated
container, delivers the fixed finite credential, completes the actual scoped task
service proof, and starts the approved recipe. Every effect has a saved intent.

An uncertain create, delivery, proof or start is not retried automatically.
Reconciliation observes only the original run. If no container ID reached storage,
the adapter discovers the deterministic original and validates its full identity
and isolation before retaining the observed ID. An absent resource after a create
intent remains unknown; it does not authorize recreation or prove a stop.

Cancellation saves its request first and fences further dispatch. It joins the
original in-flight dispatch before stopping the exact container, with a fresh
cancellation permission check at the stop boundary. A cancellation remains pending
until physical observation confirms the stop. Once admitted, that exact stop and
join remain owned if the caller is later revoked or its observer times out. The
original caller must still pass a fresh permission check before receiving a
result; a fresh authorized service query can report the retained physical truth.
This completion ownership permits no new start or authority renewal.

When durable history proves that
container creation was never dispatched, cancellation can confirm that no task
started. A lost credential preparation result still leaves its original retained
generation available for current service retirement; it does not cause a new
credential generation.

Retirement requires a confirmed terminal physical resource, a saved fence that
proves no container dispatch occurred, or exact verified cleanup of a container
whose create reply was lost before its supervisor started. In that last case,
cancellation stays pending until the container owner checks its full identity,
confirms a nonrunning created state, joins its users and removes the exact ID.
A pending running resource, absence or changed identity does not pass this check. The credential owner joins its private
users before the container adapter joins its relay and removes the exact owned
container. Private history and the task reservation remain retained. Retirement
is not broker revocation; the existing identity administrator separately revokes
the task transport. The finite credential and container supervisor retain their
original expiry limits. A new generation requires a new approved plan/run.

Shutdown joins owner jobs and private clients, then checkpoints the container
adapter without stopping retained work. Observer cancellation does not cancel an
accepted owner job. If shutdown times out, the same owner can retry after the
original job joins. Host restart uses observation and cleanup of the original;
it cannot renew the old start request or resume an uncertain effect.

The native owner returns only run references and truthful phase/step information.
The later typed Process receiver maps these to the existing receipt and outcome
contracts. It remains responsible for its caller and child boundaries. This owner
does not implement scheduling, general settings, team/provider integration or
other platforms. Qualification targets native macOS ARM64 with Docker Desktop.
