# P02 protected kernel and legacy preservation preflight

This is a read-only audit of the accepted P00 design and the existing runtime at `9db01f2d2ff6656d3f2c7fd8f9567fb421104605`. The accompanying JSON binds the files actually inspected. This record proposes implementation seams and tests. It does not accept P02-T06, change boot behavior, or claim that future tests have passed.

The safe starting point is an opt-in Go launcher and four separately supervised protected processes beside the legacy Python hub. Keep the legacy launcher and all domain behavior available. Give the new assembly separate profile, process and storage ownership. Do not reuse the legacy hub's database, socket, token, PID file, configured federation account or tmux sessions as kernel resources.

## Accepted boundaries

`delivery/decisions/acceptance.md` accepts D01–D06, S01–S05, L01–L05 and the original context package. It supersedes pending-review wording retained in the historical decision files. P01 promoted executable v1 schemas and independent SDK validation. Use those current schemas rather than introducing a second 0.1 runtime ABI.

The release-owned assembly has exactly `boot`, `kernel-lifecycle`, `internal-communication` and `exported-status`. Verify the release authority, manifest digest, binary digests and compatible kernel API before starting children. The v1 SDK checks exact distinct membership; JSON Schema's unique objects alone would allow repeated IDs with different digests. Passing shape validation does not establish trusted release provenance or permission to execute a supplied entrypoint. Reject mismatched, missing, extra or substituted members before spawning any child. Entrypoints must resolve inside the installed, reviewed release; a caller-provided path is not sufficient authority.

Use separate processes initially, as D02 recommends. Every exchange between protected plugins uses NATS. The launcher may resolve configuration, hold the pre-broker ownership lock, inspect the approved Docker endpoint, start the selected Compose project and supervise owned processes. These infrastructure operations do not create a second runtime command bus. Ordinary plugins cannot replace the assembly or issue kernel commands through CLI, HTTP, MCP, files, direct calls or borrowed credentials. A deployment administrator stopping an installed process remains a distinct installation privilege.

Separate the system, protected, application and organization/project accounts. Export only permitted kernel information. Do not export internal lifecycle subjects, broad wildcards, reply subjects that enable a command path, management APIs or broker credentials. A domain or subject name alone is not an account boundary. Ordinary `kernel-status` capability is subscribe-only; enforce this with actual broker permissions independently of both SDKs. Assemble application status outside the kernel. Missing identity, Jev, provider, domain owner or optional plugin may make application capability unavailable, but cannot prevent the protected kernel from becoming ready on its own terms.

Immutable PluginContext and per-operation OperationContext remain the destination contract. Preserve package, instance, hub, operation, payload, actor, scope, grant, revision, task/run/attempt and trace identities. A context carries scoped references and compatible handles, not the parent's environment, database object or unrestricted NATS client. Private children do not own borrowed services. Full ordinary plugin construction, nested lifecycle and production enrollment remain P03/P04 work; P02 must avoid interfaces that preclude those accepted requirements.

Relevant source reuse must be compared to the eventual P02 candidate. Original failed provider diagnostics remain immutable history; no provider launch is needed for this preflight.

## Provisioning risks requiring focused tests

`admin.provision` calls `update_stream` for every existing stream. It therefore changes retention, subjects, duplicate windows and replicas without a separately reviewed migration. Existing KV buckets are accepted by `key_value` without history, TTL or replica comparison; a broad exception leads to attempted creation. An interrupted operation may leave only a subset provisioned. These are existing behaviors, not newly executed failures in this audit.

HUB-15-C01 needs an actual isolated baseline provisioning pass, second pass and exact inspection of stream and bucket policies. Compare baseline to the separately approved P02 profile, including unchanged resources and outstanding work. HUB-15-C02 needs missing Python dependency, bad/missing credential, wrong endpoint/CA, revoked account and interruption at each provisioning boundary. Existing live federation tests establish connection and application behavior, but do not explicitly assert this complete twice-provisioned policy matrix or every TLS/error case. Do not label those checks passed from the full-suite count alone.

A new profile must inspect and report policy mismatch before changing existing storage. Keep a documented distinction between absent resources that may be created and existing incompatible resources that require explicit migration. Use `finally`-style owned connection cleanup for the new implementation's failure paths; current `provision`/`push` close only after success. Never execute `fedharness.Circle.reset` or test kind/cluster reset against user resources. New fixtures need fresh stores, accounts and explicit ownership sentinels.

## Rollback and acceptance conditions

P02 rollback disables the opt-in new runtime and returns to the retained legacy entrypoint. Stop only exact owned new children/resources; closing a client must not stop a shared healthy instance. Preserve volumes, release/profile metadata, legacy homes, credentials, aliases, database files, pending outboxes and reservations. Do not run `down -v`, prune, force-recreate, broad process killing, silent context changes or legacy imports. Do not restore an old legacy database over work written by another active owner.

Required rollback fixtures cover failure before any spawn, partial child startup, broker loss, interrupted provisioning, concurrent owner exit and incompatible release. Prove byte/identity preservation of sentinel legacy configuration and logical state, unchanged warm-reuse records and no takeover of another user's listener, process, profile or volume. Separate config-byte equality observations from proof that unrelated settings were preserved.

Before preflight acceptance, root must review the exact intended source list and scope, baseline gaps, owner/identity separation, proposed status and permission contracts, mapping of HUB-15 and cross-phase callers, and assignment of the tests above. Any capability reduction or migration needs its own approved comparison before implementation. Preserve existing FED registry entries and diagrams; register new applied PLAN-03/05/07 locations and how/where/why/tradeoffs in the implementation change. The audit adds no new pattern and does not mark planned entries implemented.
